# BEAR: завершённое сравнение и внесённые улучшения

Дата: 03.11.2026. Наша сборка: `bear-fusion-lab` + неизменённое ядро
`bear-text-beta`. Сравниваемая версия участника: `test_dedoc_qdrant`, commit
`a48d88d21ba6ece0fc37eb1f91f18905705dec7f`. Список удалённых веток повторно
проверен; ветка по-прежнему указывает на этот commit. Исходники участника не изменены.

## 1. Принятое решение

Сохраняем наши контракты блоков, источники, независимую проверку покрытия,
лимиты полного входа модели и маршрутизацию
`whole → structural → semantic → recursive → safe repair`.
Наличие одного `section_path` само по себе не становится признаком структуры.

Добавлены полезные идеи участника: связь поискового чанка с родительским
разделом, breadcrumb, объединение помещающихся в бюджет ячеек одной строки.
Для кода сохраняется наш разбор Markdown/HTML; найденная ошибка HTML-примеров
исправлена. Семантическая ветвь остаётся доступной, но её превосходство по качеству
не доказано. Docling подтверждён как более сильный кандидат для сложных PDF-таблиц;
он не заменяет автоматически нынешний PDF-парсер демо.

## 2. Что реализовано

### Родительские разделы и контекст

`src/bear_fusion/parents.py`:

```python
attach_parents(result: ProcessingResult) -> list[dict]
expand_context(envelope: dict, chunk_id: str, counter, max_tokens: int = 480) -> dict
```

`attach_parents` вызывается после независимой проверки чанков. Создаёт корневой
раздел и дерево заголовков; каждый раздел хранит `id`, `parent_id`, `title`,
`section_path`, `block_ids`. UUIDv5 учитывает tenant, Space, документ, версию,
checksum, профиль обработки и идентификатор блока заголовка. Повторяющиеся названия
разделов не сливаются. Повторный запуск с теми же данными даёт те же parent ID.

В `Chunk.metadata` добавлены:

- `parent_id: str`, `parent_ids: list[str]`;
- `chunk_order: int` — порядок внутри основного родительского раздела;
- `breadcrumb: str` — путь раздела;
- для кода: `code_languages: list[str]`, `code_block_ids: list[str]`,
  `code_parts: dict[str, dict]` с номером части и общим числом частей.

`expand_context` берёт найденный чанк и соседние чанки того же раздела из того же
результата обработки. Выход содержит текст, упорядоченные ID чанков, источники,
контекст документа, generation ID, число токенов и `truncated: bool`.
Проверяется бюджет; исходный чанк должен в него помещаться. Переходов к другому
документу или поколению нет. Это расширение контекста, а не гарантия восстановления
всего большого раздела в одном ответе. Индексируемые тексты и векторы не меняются.

Демо поддерживает `POST /context`; `POST /search` с `expand=true` возвращает
`expanded_context`. Интерфейс уже отправляет этот параметр.

### Табличные строки

`src/bear_fusion/tables.py`, `TableProcessor.process` сначала строит проверяемые
фрагменты ячеек, затем жадно объединяет соседние фрагменты одной строки, пока
полный вход модели вместе с заголовками раздела укладывается в бюджет.
Заголовки таблицы сохраняются. Широкая строка разделяется на несколько групп;
длинная ячейка — на фрагменты с контекстом. Текст не обрезается.

Для составного чанка используется `table_contract=cells-v2` и
`cell_segments: list[dict]`. Каждый сегмент сохраняет `cell_id`, `value_start`,
`value_end`, `prefix`. Независимый валидатор проверяет исходные значения,
заголовки, отсутствие смешения разных строк, пропусков и повторов.
Небольшая контрольная строка с выручкой `120` и `150` теперь доступна в одном
поисковом результате. Старый путь разбиения больших значений сохранён.

### Код

`src/bear_fusion/markdown_adapter.py` различает настоящий HTML-блок документа
и fenced/indented code по диапазонам исходных Markdown-токенов.
Раньше пример с языком `html` мог ошибочно очищаться как разметка.
Теперь `<script>`, HTML-комментарии и теги внутри примера остаются кодом;
обычные комментарии вне примеров по-прежнему исключаются.

Язык и порядок частей большого кода доступны в metadata. Тест проверяет
непрерывное покрытие всего кодового блока и совпадение исходных подстрок чанков,
включая пробелы и отступы. Автоматическое восстановление AST и разбиение по
функциям не заявляются.

## 3. Реальный семантический инференс

Артефакты: `artifacts/semantic-live/corpus.json`, `report.json`.
Скрипты: `experiments/e5_onnx_server.py`, `semantic_live.py`.

Использована настоящая `Xenova/multilingual-e5-small`, ONNX int8, на основе
`intfloat/multilingual-e5-small`. Ревизия
`761b726dd34fb83930e26aab4e9ac3899aa1fa78`; SHA256 ONNX-файла:
`4d24e2bc01a447951524466ef533e52944bf48509e6552810bcee1a2711cb02c`.
Векторы: 384 измерения, attention-mask mean pooling, L2-нормализация.
Усечение входа отключено; превышение 480 токенов вызывает ошибку.

Это локальный ONNX-сервис с совместимым HTTP-протоколом, **не сервер Infinity**.
Наша настоящая Infinity-обёртка вызывает его по HTTP. В семантический алгоритм
участника через его конструктор передан адаптер того же реального провайдера.
Векторы не подменялись. Нативный Qwen3-стек участника в этом сравнении не запускался.

Корпус: 8 специально составленных текстов без заголовков, 4 русских и 4 английских,
24 размеченных вопроса. Финальный поиск — cosine по реальным E5 passage/query
векторам сразу по всем документам. Правильный результат должен содержать ответ
и принадлежать ожидаемому документу. Целевая длина 96 токенов нужна для проверки
границ; это не замена рабочего профиля 320 токенов.

| Вариант | Чанков | Ответ в top-5 | MRR | Входов модели для границ |
|---|---:|---:|---:|---:|
| Наш adaptive | 32 | 24/24 | 0.9583 | 158 |
| Наш принудительный semantic | 32 | 24/24 | 0.9583 | 158 |
| Наш token/recursive | 22 | 24/24 | 1.0000 | 0 |
| Semantic участника с общей E5 | 31 | 24/24 | 1.0000 | 144 |

MRR — среднее обратного места первого правильного результата; больше — лучше.
Максимальные фактические входы E5: 90, 90, 96 и 98 токенов соответственно.
В наших семантических прогонах фактически выбрана ветвь `semantic`, ошибок и
fallback нет. Повторный реальный прогон воспроизвёл количество чанков и метрики.
Время последнего запуска записано в JSON; оно включает и финальные embeddings,
и оценку поиска, а не только определение границ.

**Вывод:** техническая работоспособность нашей семантической ветви подтверждена.
На этом небольшом корпусе рекурсивная стратегия быстрее и не хуже по метрикам.
Semantic участника немного лучше нашего по MRR, но не лучше recursive. Это не
доказательство преимущества на любых документах: выборка мала, пороги и
токенизаторы различаются. Не меняем автоматически рабочую политику по 24 вопросам;
для следующего выбора нужны реальные корпоративные вопросы и длинные смешанные
документы с одинаковым целевым токенизатором.

## 4. Парное сравнение настоящих PDF/OCR

Скрипт: `experiments/final_paired.py pdf`.
Полный отчёт: `artifacts/final-pdf/report.json`; каждый файл проверен обеими
реализациями. SHA256 входов, расположение полных результатов, warnings, размеры
чанков и ресурсы сохранены в отчёте. Использован полный parser/chunker участника,
а не только экспорт Docling. Модели заранее закэшированы; каждый документ
обрабатывался в отдельном процессе. Время включает запуск процесса и библиотек.
Часть прогона шла одновременно с тестами кода, поэтому это ориентировочные
ресурсные измерения, а не строгий производительный benchmark.

| Документ | Наша версия, с / пиковый RSS МБ | Версия участника, с / МБ | Проверенный результат |
|---|---:|---:|---|
| W3C dummy.pdf | 6.47 / 384 | 37.53 / 1042 | Обе извлекли контрольный текст |
| Attention Is All You Need, 11 страниц | 10.11 / 425 | 146.13 / 1697 | Связная строка сложной таблицы есть у участника; у нас результат partial |
| OCRmyPDF linn | 38.78 / 482 | 66.83 / 1233 | Покрытие уникальных слов эталона: 97.67% против 93.02% |
| OCRmyPDF skew | 39.61 / 474 | 54.47 / 1131 | Покрытие: 97.67% против 92.73% |

Все 8 запусков завершились. Завершение не означает правильного распознавания.
У обеих версий на сканах размер диска распознан ошибочно как `314"`; поэтому
приведённые проценты **не являются точностью символов, чисел или порядка чтения**.
Покрытие считается как `|слова_эталона ∩ слова_извлечения| / |слова_эталона|`;
эталон берётся из OCRmyPDF `linn.txt`. Skew — вариант той же страницы.

В статье полный путь участника сохранил в одном чанке `Transformer (big)`,
`28.4`, `41.0`; наш путь этого не сделал. Отдельный реальный структурный экспорт
Docling содержит 4 табличных объекта, включая нужную таблицу результатов.
Один из объектов — блок авторов, классифицированный как таблица: число объектов
само по себе не означает качество. Формулы и все объединения ячеек не размечались.

Для запуска Docling потребовались совместимые зависимости, torchvision,
загрузка моделей и перенос нативных ресурсов в путь без кириллицы.
Проверенная среда: Python 3.11, Dedoc 2.8, Docling 2.145.0, Chonkie 1.7.0,
torch 2.14.1, transformers 5.22.1, python-docx 1.2.0; зависимости сравнения
подключены из отдельного overlay, исходники не правились.
Docling layout revision: `8f39ad3c0b4c58e9c2d2c84a38465abf757272d8`;
table-model bundle revision: `fc0f2d45e2218ea24bce5045f58a389aed16dc23`.
Контейнер для этих запусков не потребовался. Это не проверка установки с нуля
на другом компьютере. Первоначальная загрузка моделей была заметно дороже.

**Решение:** наш быстрый PDF/OCR-путь сохраняем базовым. Для сложных таблиц
следующий адаптер целесообразно строить на структурном Docling Document,
передавая ячейки и provenance напрямую в общие блоки, без потерь при цепочке
`Markdown → HTML → Dedoc`. Этот адаптер ещё не подключён к демо; текущий тест
обосновывает его выбор, а не подтверждает готовую универсальную интеграцию.

Источники корпуса: [W3C PDF](https://www.w3.org/WAI/ER/tests/xhtml/testfiles/resources/pdf/dummy.pdf),
[статья NeurIPS](https://papers.neurips.cc/paper_files/paper/2017/file/3f5ee243547dee91fbd053c1c4a845aa-Paper.pdf),
[OCRmyPDF test resources](https://github.com/ocrmypdf/OCRmyPDF/tree/main/tests/resources).
Исходные URL и SHA256 также находятся в локальных манифестах корпуса.

## 5. Дополнительное сравнение кода

`experiments/final_paired.py code`, `artifacts/final-code/report.json`.
6 контрольных документов, 12 запусков: HTML-пример, Python с отступами и русским
комментарием, Rust внутри списка, длинный Python-блок, длинный идентификатор,
HTML `<pre>`. Это синтетические проверки краевых случаев, не новый публичный корпус.

- На четырёх небольших примерах наш чанк сохраняет код целиком и точно.
  Участник сохраняет все проверенные непробельные символы, но дробит примеры;
  отступы Python/Rust/HTML-pre в parsed tree не совпадают с оригиналом.
- Длинный Python-блок: у нас 10 частей кода и отдельный заголовок, у участника
  200 отдельных строк кода и заголовок. Отсутствие потерь непробельных символов
  подтверждено у обеих версий. Смысловая полезность именно 10 против 200 частей
  поисковыми вопросами отдельно не оценивалась.
- Длинный идентификатор: у нас максимум 320 E5-токенов; у участника 863 для
  token и 1343 для recursive. Такой вход несовместим с E5-small 512, хотя может
  помещаться в другую выбранную модель. Это несовпадение токенизатора и модели,
  а не доказательство поломки при любом его embedding-провайдере.
- У нас есть метаданные языка/порядка продолжений. Сопоставимые поля
  `code_languages` в проверенных чанках участника отсутствуют.

**Решение:** заменять наш путь обработки кода нецелесообразно.
К нему добавлены полезные Parent-Child связи участника и наша информация о частях;
исправление fenced HTML проверено заново. AST-парсер не добавлялся без доказанной
необходимости и отдельной оценки поддержки языков.

## 6. Чем сильнее API, индексация и retrieval участника

По сравнению с **нашим Fusion-демо**, где есть BM25 и просмотр этапов, у участника
шире прикладной слой: `IndexDocumentService`, `SearchService`, Qdrant-адаптер,
dense + sparse, объединение RRF, опциональный reranker, ограничения выдачи и
фильтры session/tenant/Space. Это готовые точки интеграции, а не доказанное
превосходство итогового поиска на реальном корпусе.

У старого `bear-text-beta` тоже есть Qdrant и управление поколениями.
Поэтому неверно говорить, что в нашей системе вообще нет индексации.
В текущем Fusion-демо она намеренно не включена; `accepted_for_indexing=false`.

Повторно выполнены тесты участника: `test_index_document_service.py`,
`test_search_service.py`, `test_rrf.py`, `test_inmemory_vector_store.py` —
**217 passed**. Это реальные тесты application-кода, но с тестовыми векторами и
in-memory хранилищем; живые Qdrant/SPLADE/reranker этим не подтверждены.

Отдельный `experiments/index_failure_probe.py` проверил отказ записи:
успешно индексированы 3 points, затем у настоящего `IndexDocumentService`
искусственно вызвана ошибка upsert в тестовом store. После ошибки осталось
0 points. Причина — `delete` перед `upsert` в
`application/index_document.py:302–303`. Модельные провайдеры в этом опыте тестовые;
он проверяет последовательность операций, не качество embeddings.

**Решение:** переиспользовать идеи портов, гибридного поиска и транспортного слоя,
но не переносить delete-before-upsert. Сохранить нашу запись нового поколения,
проверку полноты, активацию и последующее удаление старого. Наши
`bear-text-beta/tests/test_indexing.py` — **12 passed**, включая частичную запись,
повтор задания, запрет активации устаревшего/удалённого документа и восстановление.
Полная новая Qdrant-интеграция Fusion в рамках этой доработки не включалась.

## 7. Итоговая проверка и ограничения

- Наши тесты парсинга/чанкинга/демо: **52 passed**.
- Проверки индексации нашего базового ядра: **12 passed**.
- Выбранные application/retrieval-тесты участника: **217 passed**.
- Ruff для изменённых модулей и новых проверок: без ошибок.
- Реальное локальное HTTP-демо: MD, PDF с таблицей, PDF-скан, DOCX — **4/4**;
  все четыре этапа доступны, поиск, целая короткая строка и Parent-Child
  expansion проверены HTTP-запросами. Отчёт:
  `artifacts/demo-acceptance/http-report.json`.
- Реальные семантические прогоны и парные PDF/код-прогоны сохранены отдельно;
  их нельзя складывать с unit-тестами в одну «точность продукта».

Остаются предметом следующих работ: прямой Docling-адаптер, сложные/сканированные
таблицы, точность чисел OCR, размеченные реальные поисковые вопросы, живой
гибридный Qdrant-стек и воспроизводимая установка на чистом устройстве.
Жёсткая изоляция ресурсов ОС не заявляется. Существующие процессные лимиты,
проверки покрытия и честная диагностика `partial` сохранены.

Запуск: `./start-demo.ps1`; адрес `http://127.0.0.1:8765/`.
Проверять изменения нужно новой загрузкой документа: старые результаты не
переписываются. Подробная инструкция находится в `DEMO.md`.
